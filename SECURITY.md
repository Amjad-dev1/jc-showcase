# Security Design

This document explains the security model of the platform: what it protects, who it
protects against, and why each control is built the way it is. Links point to the
real source files in [`samples/`](samples).

---

## 1. What is being protected

| Asset | Why it matters |
|---|---|
| Customer personal data | Names, emails and phone numbers of everyone who registers |
| Payment integrity | A registration marked "Paid" must correspond to money actually captured |
| Admin accounts | Full read access to customer data and control of the catalogue |
| Server secrets | Database credentials, gateway API password, session signing key |
| Availability | A registration form that is down during a launch loses real revenue |

## 2. Threat model

| Threat | Example | Primary controls |
|---|---|---|
| Payment fraud | Forging a "payment succeeded" callback, or posting `paymentState: "Paid"` directly | Server side pending record, HMAC token, gateway verification, schema stripping |
| Account takeover | Credential stuffing or brute force against the admin login | Argon2id, rate limiting, uniform failure responses |
| User enumeration | Timing the login, or probing which emails registered for an event | Dummy hash timing equalisation, rate limited check email endpoint |
| Broken access control | Calling an admin Server Action or API route directly | `requireAdmin()` in every handler, proxy subtree guard |
| CSRF | A third party page submitting forms with the admin's cookies | `Origin` check in the proxy, `SameSite` cookies |
| Injection | SQL injection, HTML injection into outgoing email, XSS | Parameterised queries, escaping, strict CSP |
| Information disclosure | Stack traces, driver errors, PII in logs | Error envelope, constraint name mapping, redacting logger |
| Bot abuse | Contact form spam, scripted registrations | Turnstile (fail closed), rate limits |
| Secret leakage | A server module accidentally bundled into client JavaScript | `server-only` imports enforced by the build |

## 3. Authentication

**Source:** [`auth/password.ts`](samples/src/lib/server/auth/password.ts),
[`auth/config.ts`](samples/src/lib/server/auth/config.ts)

- **Argon2id** with 64 MiB memory, 4 passes, 1 lane. Memory hard hashing makes GPU
  cracking of a stolen database far more expensive than bcrypt or SHA based schemes.
- **Legacy compatibility without a reset.** The old PHP system produced standard PHC
  strings (`$argon2id$v=19$m=65536,t=4,p=1$...`). Because the parameters live inside
  the hash, the new system verifies legacy hashes directly. A unit test uses a real
  hash generated by PHP to prove it, since this was the riskiest assumption of the
  migration.
- **Timing equalisation.** If the email does not exist, the login still verifies the
  password against a dummy Argon2 hash generated at startup. Without this, "unknown
  user" would return measurably faster than "wrong password" and the identical error
  message would be meaningless.
- **Malformed hashes fail closed.** A corrupt hash returns `false`, never a 500 that
  would confirm the row exists.
- **Sessions** are Auth.js JWTs in signed, `HttpOnly`, `SameSite` cookies
  (`__Secure-` prefixed over HTTPS), expiring after 8 hours. The `admin` role is
  written into the token at sign in from the database result, never from any input.
- **Password change** enforces every rule on the server (old password verifies, new
  one matches its confirmation, 8 to 25 characters, differs from the old) and then
  forces re-authentication.

## 4. Authorization

**Source:** [`proxy.ts`](samples/src/proxy.ts),
[`auth/guards.ts`](samples/src/lib/server/auth/guards.ts)

Two layers, deliberately redundant:

1. **The proxy** redirects any request under `/admin/**` without a session cookie
   to the login page. A new admin screen is protected the moment it exists, so
   protection cannot be forgotten by omission.
2. **`requireAdmin()`** is called explicitly at the top of every admin route handler
   and Server Action. This is the real check: it validates the session itself, not
   just the presence of a cookie.

The second layer exists because Next.js Server Actions are compiled into public POST
endpoints addressed by an action ID, not by path. A proxy rule on `/admin/**` does not
cover them, and being defined inside an admin only component grants no protection.

## 5. CSRF

**Source:** [`proxy.ts`](samples/src/proxy.ts)

Every `POST`, `PUT`, `PATCH` and `DELETE` to `/api/**` or `/admin/**` is checked in the
proxy: if an `Origin` header is present and does not match the host, the request is
rejected with `403` before reaching any handler. A missing `Origin` is allowed because
`navigator.sendBeacon` omits it on same origin requests, and the lead capture endpoint
depends on beacons. Combined with `SameSite=Lax` cookies this closes cross site writes.

## 6. Payment integrity

**Source:** [`payment-service.ts`](samples/src/lib/server/services/payment-service.ts),
[`checkout-token.ts`](samples/src/lib/server/integrations/checkout-token.ts),
[`mpgs.ts`](samples/src/lib/server/integrations/mpgs.ts)

```
1. POST /payments/session
   ├─ validate input, check event is open and accepts payment
   ├─ refuse duplicate email BEFORE charging anyone
   ├─ INSERT pending_registrations (payload, amount from DB)     <- persisted first
   ├─ create gateway session (server to server)
   └─ return { sessionId, checkoutToken = HMAC(orderId, eventId, sessionId, exp) }

2. Customer pays on the gateway's hosted page (card data never touches our server)

3. POST /payments/verify { checkoutToken }
   ├─ verify HMAC in constant time, check expiry        -> 403 if forged or expired
   ├─ load pending row; if already consumed, return the same outcome (idempotent)
   ├─ GET order from the gateway API
   ├─ PAID only if result == SUCCESS AND status == CAPTURED
   │    (authorised but uncaptured -> PENDING_REVIEW, never auto confirmed)
   └─ finalize in one transaction:
        by order_id  -> return existing
        by event+email -> attach order, mark Paid
        else insert  (unique constraint catches races; re-read and converge)
```

Properties this guarantees:

- **The client is never believed about payment.** The token only says which order to
  ask about; the outcome, amount and currency come from the gateway.
- **The amount is never client controlled.** It comes from the event type row.
- **No lost payments.** Because the payload is stored before the gateway call, a
  payment whose response never arrives can still be finalized later.
- **No double registrations.** Refreshes, duplicate callbacks and concurrent
  verifications all converge on one row, proven by integration tests that run them
  in parallel against real PostgreSQL.
- **Order IDs are unguessable.** Generated from `crypto.randomUUID()`, with uniqueness
  enforced by a database constraint rather than a racy pre check.

## 7. Input validation and mass assignment

**Source:** [`schemas/public.ts`](samples/src/lib/shared/schemas/public.ts)

All input is parsed with Zod schemas shared by the browser form and the server. The
browser copy is only a convenience; the server parses independently on every request.
The public registration schema has **no** `orderId`, `paymentState` or paid flag, and
unknown keys are stripped, so a request that tries to mark itself paid is stored as
`Pending` with no order ID. This was verified live (see the README).

## 8. Rate limiting and bot protection

**Source:** [`ratelimit.ts`](samples/src/lib/server/ratelimit.ts),
[`turnstile.ts`](samples/src/lib/server/integrations/turnstile.ts)

| Limiter | Window | Key | Purpose |
|---|---|---|---|
| Admin login | 15 min | IP | Brute force and credential stuffing |
| Check email | 1 min | IP + event | Stops enumeration of an event's attendee list |
| Contact | 1 hour | IP | Spam |
| Payment session | 1 min | IP | Gateway abuse and order flooding |

- **Sliding window**, not fixed, so an attacker cannot double the rate at a window
  boundary.
- **Shared Redis store**, because in process counters reset per instance and never
  actually limit anything on serverless or multi instance hosting. An in memory
  fallback exists for development only, logs a warning whenever it is used, and an
  `assertRateLimitReady()` check is provided for production startup.
- **Deliberate failure modes.** A rate limiter outage *fails open* (the endpoints
  behind it are still validated and authenticated, and a dead registration form is
  worse). A Turnstile outage *fails closed*, because "accept everything" would open
  the exact abuse it exists to stop.
- **Turnstile hostname binding**: a token solved on another site is rejected even
  though Cloudflare reports it as valid.
- Client IPs from `X-Forwarded-For` are treated as untrusted, used only as limiter
  keys, and truncated to bound key cardinality.

## 9. Error handling and information disclosure

**Source:** [`http.ts`](samples/src/lib/server/http.ts),
[`shared/errors.ts`](samples/src/lib/shared/errors.ts),
[`repositories/errors.ts`](samples/src/lib/server/repositories/errors.ts)

- Every route handler is wrapped by `handleRoute()`. Anything that is not a modelled
  `AppError` becomes a generic `INTERNAL_ERROR`; the detail is logged server side and
  the client receives only a request ID to quote.
- Messages come from a fixed table keyed by error code, never from the caught
  exception.
- PostgreSQL errors are translated by **constraint name** (declared in the DDL), so a
  unique violation becomes a clean `409` without ever echoing
  `Key (event_id, email)=(...)` back to the caller. Unknown database errors become
  a generic 500.

## 10. Logging and privacy

**Source:** [`logger.ts`](samples/src/lib/server/logger.ts)

Redaction is structural, not a convention call sites have to remember:

- Values under sensitive keys (`email`, `mobile`, `password`, `token`, `cookie`,
  `cardNumber` and more) are replaced with `[redacted]` at any depth.
- Emails inside free text are masked to `j***@example.com`, enough to correlate two
  log lines, not enough to contact anyone.
- Phone shaped digit runs become `[phone]`.
- Error messages and stack traces go through the same redaction.
- Recursion is depth limited so a cyclic object can never make the logger throw.

## 11. Browser hardening

**Source:** [`next.config.ts`](samples/next.config.ts)

| Header | Value |
|---|---|
| Content-Security-Policy | `default-src 'self'`, scripts only from self, Turnstile and the gateway; `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'self'`. `unsafe-inline` scripts allowed only in development |
| Strict-Transport-Security | 2 years, `includeSubDomains`, `preload` |
| X-Content-Type-Options | `nosniff` |
| X-Frame-Options | `SAMEORIGIN` |
| Referrer-Policy | `strict-origin-when-cross-origin` |
| Permissions-Policy | camera, microphone, geolocation disabled |
| X-Robots-Tag | `noindex, nofollow` on `/admin` and `/api` |
| Cache-Control | `no-store` on every API response |

Every third party origin in the CSP is one the application actually loads; nothing is
listed speculatively.

## 12. Secrets

- All configuration comes from environment variables, validated at startup. The app
  refuses to start half configured and names the missing variable.
- No secret exists in source. Every credential inherited from the legacy system is
  treated as already exposed, and the go live checklist requires generating new
  values at the source rather than reusing old ones.
- Every module under `src/lib/server` imports `server-only`. If client code imports
  one, the **build fails**, which is what keeps the database URL, gateway password
  and signing secret out of the browser bundle.
- Outbound email uses a single SMTP configuration with certificate verification that
  cannot be turned off.

## 13. Verification

Security controls are pinned by tests so a regression is caught as a failing build,
not discovered in production. Highlights from
[`security.test.ts`](samples/tests/unit/security.test.ts),
[`password.test.ts`](samples/tests/unit/password.test.ts) and
[`payments.test.ts`](samples/tests/integration/payments.test.ts):

- a tampered token payload, tampered signature, malformed token and expired token are
  all rejected
- `SUCCESS` without `CAPTURED` is never treated as paid
- 5,000 generated order IDs produce no collisions
- an `<img onerror>` and `<script>` payload in a contact message arrive as inert text
- nested PII and PII inside error stacks are redacted
- database detail text never appears in an error envelope
- a real PHP generated Argon2id hash verifies
- the dummy hash path costs about the same as a real verification
- duplicate and concurrent payment callbacks produce exactly one registration
